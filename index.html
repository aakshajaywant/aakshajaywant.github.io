Jetson × UNO Q Automated Test Bench

In progress

A small version of a production wireless-system test station. An NVIDIA Jetson Orin Nano acts as the test-automation controller and drives an Arduino UNO Q as the device under test. Instruments sit behind a common driver interface, results go to a database, and every change runs through CI.

The core is the equipment driver abstraction layer. Test cases are written against an interface, not an instrument, so you can swap an SDR, a power supply or a meter without rewriting tests.

Driver interface (Python ABC)
class Instrument(ABC):
    """Every bench instrument looks the same to a test."""
    @abstractmethod
    def connect(self) -> None: ...
    @abstractmethod
    def configure(self, **cfg) -> None: ...
    @abstractmethod
    def measure(self) -> Measurement: ...
    @abstractmethod
    def reset(self) -> None: ...

Bench architecture
  • SDR-based RF measurement pipeline for wireless checks
  • pytest test cases with a results database for trend and regression tracking
  • Built in eight phases. The last one is a validation-gap analysis: what the bench can't catch yet, and why.

Zero-Comms DUT Verification Harness

Design study

A constraint-inversion exercise: verify a device that has no communication channels at all. No UART, no debug port, no telemetry. The harness only observes. It infers device health from the physical side effects the device can't help producing.

CH·01Power-draw shape over time
CH·02LED / I/O timing patterns
CH·03EM emissions
CH·04Thermal profile
CH·05Acoustic signature
CH·06Visual inspection
CH·07Mechanical stress response
CH·08Event timing via independent sensors

This matters for black-box third-party modules, sealed products and legacy hardware where you can't add instrumentation to the firmware.

Edge-AI Validation on the Arduino UNO Q

Exploration

The UNO Q is most useful when real-time MCU control, on-device AI and connectivity work together, not as a generic single-board computer. This work maps how App Lab "bricks" on the Linux/MPU side interact with MCU-side test harness code, and how to validate AI behaviour on the device.

  • Training in TensorFlow / PyTorch, then optimisation and deployment through Edge Impulse
  • The .eim model artifact, not raw .tflite or .pt, is what actually gets deployed, so that is what validation has to test
  • Kept separate from the TensorFlow Lite for Microcontrollers path for MCU-only targets
